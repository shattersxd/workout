# Workout Routine — PWA трекер тренировок

Личное приложение для зала. Один пользователь (iPhone 11 Pro Max, Safari,
установлено на домашний экран). Интерфейс на русском. Хостинг — GitHub Pages:
`https://shattersxd.github.io/workout`.

Отвечай и пиши комментарии в коде по-русски, как в существующем коде.

---

## Как собирается проект

Нет бандлера и нет шага сборки в рантайме. Приложение — **один HTML-файл**,
который в браузере компилирует себя сам через Babel standalone.

```
src/shell/head.html          <- <head>, CSS, лоадер, манифест, иконки, бутстрап Babel
src/workout_tracker.jsx      <- ВСЁ приложение: данные + компонент App
src/shell/tail.html          <- ErrorBoundary, ReactDOM.createRoot, </html>
        |
        v  python3 scripts/build.py
index.html                   <- то, что отдаётся GitHub Pages

vendor/                      <- React 18.3.1, ReactDOM 18.3.1, Babel 7.23.10 (не с CDN)
sw.js                        <- настоящий service worker, регистрируется из index.html
```

**Внешних зависимостей при запуске нет.** Библиотеки лежат в `vendor/`
(версии и SHA-256 - в `vendor/README.md`, тесты сверяют суммы) и кэшируются
`sw.js`, так что приложение стартует и без интернета. Файлы в `vendor/` не
править; `.gitattributes` запрещает git менять в них переводы строк. Обновили
библиотеку - поднимите `CACHE` в `sw.js` (`sila-v7`...), иначе телефон останется
на старой копии.

### Тестовая версия (`beta/`)

Адрес `https://shattersxd.github.io/workout/beta/`, на телефоне подписана «Workout
BETA», в шапке значок BETA и вкладка «БЕТА». Здесь пробуем новое (тренер, Spotify),
не рискуя основной версией. `python3 scripts/build.py` пишет **три** файла:
`index.html`, `beta/index.html`, `beta/sw.js`; `--check` проверяет все три.
Тестовая страница = тот же код + `src/beta/*.jsx`, вставленные перед `App`
(в боевой `index.html` их нет). Швы в боевом коде минимальны: `APP_VARIANT`,
`STORAGE_KEY` / `TIMER_KEY` и проверки `typeof BetaTab === "function"`.
Подстановки в `build.py` идут через `replace_once` и падают, если не сработали.

**Изоляция обязательна**: у всех страниц на `github.io` общие `localStorage` и Cache
Storage. Поэтому данные беты лежат под `ppl_tracker_beta` / `sila_timer_beta`;
боевой ключ бета только **читает** (`readProdBackup`, одна константа
`PROD_STORAGE_KEY`), а кнопка «скопировать из основной версии» добавляет
недостающие тренировки через `mergeBackup`. Воркер беты - `beta/sw.js` со своим
кэшем `sila-beta-*`; оба воркера чистят только кэши со своим префиксом.
**На iPhone каждое приложение с экрана «Домой» хранит данные ОТДЕЛЬНО, даже при общем
адресе**, поэтому тестовое приложение не видит `localStorage` основного: прямое
копирование (`readProdBackup`) работает только в обычных вкладках и на компьютере, а на
телефоне данные переносятся **файлом** копии (`betaMergeFile`: в основной версии «ПЛАН ->
СОХРАНИТЬ», в тестовой «ЗАГРУЗИТЬ ФАЙЛ»). Анкета первого запуска рисуется через
`ReactDOM.createPortal` в `<body>` при скрытом `#root`: фиксированное окно на iPhone иногда
не доходит до нижнего края, и под ним просвечивало основное приложение. Всё это
проверяет секция 23 (в том числе настоящей компиляцией бета-страницы Babel из
`vendor/`). Любой новый файл в `src/beta/` подчиняется тем же запретам ниже.

**Тренер** (`src/beta/coach.jsx`) - локальный, на правилах, без сети и ключей.
`coachAnalyze(data, today)` - чистая функция: читает `history` и `schedule`, отдаёт
сводку (тренировок на неделе, давность последней, темп за 4 недели) и советы:
перерыв >= 10 дней, пропуски по расписанию за 2 недели, застой (>= 4 тренировки,
3 подряд без нового максимума), рекорды за неделю, перекос жим/тяга/ноги за 4
недели (только дни из расписания), резкий рост объёма недели (> 1.3x), «пора
разгрузиться» (6+ недель без лёгкой), серия недель по плану. Пороги - константы
`COACH_*`. Советы сортируются warn > tip > good, максимум 6; «СКРЫТЬ НА НЕДЕЛЮ»
пишет `data.coachDismissed[id]` (дата). Повторы не хранятся, поэтому судим только
по весам, отметкам и датам. Тесты исполняют настоящий код на синтетических журналах.

**Профиль и подбор программы** (`src/beta/profile.jsx`). Анкета при первом запуске
(`BetaOverlay` - единственный «шов» в боевом `App`, защищён `typeof`): пол, возраст,
рост, вес, цель, опыт, дней в неделю, ограничения. Хранится в `data.profile`; вес тела -
`data.bodyLog` (одна запись на дату), самочувствие 1-5 - `data.feelLog`. Чистые функции
(`profileValidate`, `profileEnergy`, `profileRecommend`, `bodyTrend`, `feelRecent`)
вынесены выше блока `// ---- Интерфейс ----` и тестируются исполнением. Подбор берёт
только существующие пресеты (`push/pull/legs/fullbody_a/b/c`): новичок - не больше 3
дней и фулбади; 4 дня - PPL + общий день; 6 дней - PPL дважды с одним выходным.
Калории - Mifflin-St Jeor, но для возраста < 16 или > 70 и ИМТ < 16 или > 40
`profileEnergy` возвращает `null` (формула там не к месту, нужен врач). Все тексты про
питание и травмы - общие ориентиры с оговоркой «обратитесь к врачу». Тренер
(`coachProfileAdvice`) учитывает анкету: напоминание о взвешивании, динамика веса
относительно цели (нужны записи с промежутком от 21 дня), низкое самочувствие,
расписание короче рекомендации. Профиль и замеры лежат в бета-данных и попадают в файл
копии, но `mergeBackup` при загрузке копии пока восстанавливает только журнал и сессии.

**Заготовки под соц-функции** (`src/beta/social.jsx`, варианты и обоснования - в
`docs/social-design.md`). Сервера нет, поэтому **модуль не делает ни одного сетевого
вызова** (тест запрещает `fetch`, `WebSocket`, `sendBeacon` и т. п. в этом файле).
Заложено: `data.schemaVersion`, `data.identity.userId` (случайный UUID, без личных
данных), `data.social` (согласия, всё скрыто по умолчанию), `socialSummary(data, today)` -
ровно тот пакет, который позже уйдёт на сервер (только число тренировок, серия, объём,
рекорды; **профиль, вес тела, самочувствие, травмы и журнал не попадают в него ни при
каких настройках**, тест проверяет это на секретных значениях), `socialLeaderboard`
(регулярность важнее абсолютных весов) и интерфейс бэкенда с локальной заглушкой
(`socialLocalBackend`), чтобы собирать UI до появления сервера. Не сделано намеренно:
`id`/`updatedAt` у записей журнала и миграция боевых данных - перед синхронизацией это
нужно, но трогает боевые данные и делается отдельным осторожным шагом.

**Соревнования «сейчас»** (`src/beta/compete.jsx`, сеть не используется, подробности и
варианты - `docs/social-design.md`, раздел 9). Четыре формата (подходы, процент плана,
личные рекорды, командная цель). В комнату уходят **только счётчики, веса - никогда**
(`socialLivePayload`, проверено тестом на «секретном» весе). Время достижения счёта
ставит сервер и не меняется при повторной отправке (так «кто раньше» не подделать).
**Боты для холодного старта**: чистая функция от (зерно комнаты, минуты), одинаковые на
всех телефонах; темп из журнала пользователя; люди вытесняют ботов с конца списка. Ведут
себя по-человечески (`socialBotTimeline`: опоздание к старту, неровный отдых, редкие
долгие паузы, каждый четвёртый бросает тренировку). **Но боты не выдаются за людей**:
значок 🤖 у имени и строка «В комнате: N человек и M бота-партнёра» обязательны, переключателя,
скрывающего пометку, нет и быть не должно (тест). В комнатах настоящие люди, обманывать их
нельзя; боты не попадают в недельные рейтинги, серии и рекорды.

**Зал - «одна большая комната»** (`ArenaPanel`, `docs/social-design.md`, раздел 10). Все видят
всех по умолчанию, но **только после явного выбора пользователя** (`social.consentAt`;
до него `socialPublishTargets` разрешает публиковать ничего). Видимость: `public` /
`friends` / `hidden`, все три равноправны на экране. Закрытые комнаты друзей (`CompetePanel`)
не зависят от зала, боты в них по умолчанию выключены. Открытый зал - с 16 лет (по анкете).
Имя по умолчанию - «Участник XXXX» из кода устройства. Зал устроен как группы до 30
человек (`socialCohortKey`, `socialShardIndex`, `socialArenaView`) плюс общий счётчик
людей; счётчика «сейчас в зале» в приложении нет, пока нет сервера (выдумывать его - обман).

**Spotify-пульт** (`src/beta/spotify.jsx`): что играет, пауза/играть, предыдущий и
следующий трек. Музыку играет приложение Spotify на телефоне (Web Playback SDK в
Safari на iPhone не работает), у нас только Web API. Вход - Authorization Code + PKCE
без секретов, нужен Client ID приложения пользователя из
developer.spotify.com/dashboard (с 2026 года владелец приложения должен иметь Premium;
для новых приложений лимит 5 пользователей). Redirect URI должен совпадать буква в
букву: `https://shattersxd.github.io/workout/beta/` (панель показывает его сама).
**Токены - отдельным ключом `ppl_spotify_beta`, не в `data`**, иначе они попали бы в
файл резервной копии. Колбэк (`?code=&state=`) обрабатывает `spBoot()` при старте
страницы, а `betaInitialTab()` возвращает после входа на вкладку БЕТА. Время в
функциях передаётся параметром (`spNow`): `now || Date.now()` ломается на нуле.
Открытый риск: в PWA с домашнего экрана iOS вход может завершиться в другом
контексте хранилища; тогда `spExchange` честно скажет, что не нашёл начатый вход.
Проверять на телефоне.
**Мини-плеер на главной** (`BetaMiniPlayer`, шов в `App` над содержимым любой вкладки,
показывается только при подключённом Spotify) и **выбор музыки** (`SpotifyPicker`:
плейлисты через `GET /me/playlists`, поиск трека `GET /search?limit=10`; запуск -
`PUT /me/player/play` с `context_uri` или `uris`). Своего сервера для этого не нужно.
Режим разработки Spotify (с февраля 2026) отдаёт в поиске не больше 10 результатов.
Состояние плеера общее: один опрос раз в 5 секунд на всех подписчиков
(`spFeedSubscribe`, таймер живёт, пока есть хотя бы один подписчик и приложение на
экране), все запросы идут через очередь `spSharedCall` и каждый раз читают токены
заново, иначе мини-плеер и панель обновили бы токен одновременно (при ротации
refresh-токена это ломает вход). Токены помнят выданные доступы (`scope`): токен без
`playlist-read-private` просит один раз войти заново, а не показывает ошибку.

**Другие музыкальные сервисы - в планах** (`docs/music-design.md`): решено пока только Spotify.
Причина выбора типа интеграции - ограничение iPhone: приложение с экрана «Домой» останавливает
звук при сворачивании или блокировке, поэтому «пульт» к приложению сервиса (как Spotify) и
«плеер внутри приложения» (радио, Jamendo, Apple Music) - разные вещи. Не обещать пользователю
фоновое воспроизведение изнутри нашего приложения.

**Тон текстов.** Тестовая версия написана на «вы», вежливо и без резких формулировок;
основная версия остаётся на «ты» (так решено заказчиком). Экраны основной версии внутри
тестового приложения (тренировка, журнал) остаются на «ты».

`build.py` только склеивает три файла и убирает границу ES-модуля:

| в `src`                                     | в `index.html`                        |
|---------------------------------------------|---------------------------------------|
| `import { useState, ... } from "react";`     | `const { useState, ... } = React;`    |
| `export default function App() {`            | `function App() {`                    |

Больше ничего не трансформируется. Поэтому **всё, что попадает в `src`, должно
быть валидным для Babel 7.23 на iOS как есть** — см. раздел «Запреты».

### Тема оформления (светлая / тёмная / авто)

Цвета в стилях приложения - **переменные CSS**, а не hex: `var(--bg-0c0c0f)` (фон),
`var(--bd-1a1a22)` (граница), `var(--tx-666)` (текст). Имя токена = роль плюс **тёмное**
значение, которое он заменяет, поэтому тёмная тема осталась прежней (сверка вычисленных
цветов старой и новой сборки на 11 экранах: 0 отличий больше 2 уровней яркости, остаток -
слитые почти одинаковые оттенки). Светлые значения лежат рядом, в блоках `:root` и
`:root[data-theme="light"]` в `head.html`.

- **Голые серые hex в стилях запрещены** (секция 24): в светлой теме они остались бы
  тёмными. Нужен серый - берите ближайший токен; новый токен добавляется в ОБЕ темы
  (тест: одинаковый набор, имя = тёмное значение, нет неиспользуемых, у каждого
  текстового токена достаточный контраст). Исключение - шесть запасных цветов дня
  (`"#444"` и т. п.), к которым дописывают прозрачность (`${c}15`): `var()` с суффиксом
  прозрачности невалиден.
- **Цвета дней как текст и обводка идут через `ink()`**: оранжевый, бирюзовый и другие
  акценты (`w.color`, `day.color`) на белом нечитаемы. `themeInk` отдаёт тот же оттенок,
  затемнённый до контраста 4.5 (в тёмной теме возвращает цвет как есть). Фон и подкраска
  (`background: w.color`, `${w.color}18`) остаются без `ink`. Тест ловит `color: ....color`
  без `ink(`. Скрипт-замена (одноразовая) оставила нетронутыми акценты с прозрачностью и
  чёрный текст на цветной кнопке: они работают в обеих темах.
- **Выбор темы**: `auto` / `light` / `dark`, по умолчанию **`dark`** (ничего не меняется,
  пока человек не выберет), переключатель в «Мой план -> ТЕМА». Хранится **отдельным
  ключом `sila_theme`**, а не в `data` (иначе поехал бы в файл резервной копии). Его
  читает короткий скрипт в `<head>` ДО первого кадра (иначе мелькнёт не та тема) и ставит
  `data-theme` на `<html>`; правила скрипта и `themeResolve` в приложении обязаны
  совпадать, тест гоняет оба на всех сочетаниях. `auto` следит за `prefers-color-scheme`
  вживую и после возврата из фона (на iOS событие `change` в фоне может не прийти).
- **Статус-бар iPhone**: при `black-translucent` его текст всегда БЕЛЫЙ, на светлой
  странице часы бы пропали. Поэтому в светлой теме под статус-баром лежит тёмная полоса
  (`body::before`, высота `env(safe-area-inset-top)`; в Safari без установки на экран
  высота 0). **На телефоне ещё не проверено** - смотреть шапку в светлой теме.
- **Тестовая версия всегда тёмная**: её панели (`src/beta/*.jsx`) написаны на hex под
  тёмный фон, переключателя там нет, ключ темы свой (`sila_theme_beta`, его никто не
  пишет). Перевести бету на токены - отдельная задача.

### Рабочий цикл

```bash
python3 scripts/build.py && node tests/test_pwa.js
```

Правим **только `src/`**. `index.html` — артефакт сборки; редактировать его
руками нельзя, следующая сборка затрёт правку. Коммитить `index.html` нужно,
потому что GitHub Pages отдаёт именно его.

Перед деплоем должно быть **331/331 PASSED**. Красный тест — это не повод
править тест, это повод править код (исключения — ниже).

Проверить, что закоммиченный `index.html` соответствует `src`:

```bash
python3 scripts/build.py --check
```

## Запреты (каждый — это упавшее на iPhone приложение)

### 1. Не-ASCII символы внутри строковых литералов JS

Babel 7.23 в Safari на iOS падает на не-ASCII символах в строковых литералах.
Исключения, которые работают: **кириллица** (U+0400–U+04FF), **знак градуса**
`°` (U+00B0) и **эмодзи** (U+1F000+).

Запрещены внутри строк, в том числе: `× · → ← № ✓ ✗ ✎ − – — ⚠ ⇄ ▾ ▴ ▲ ▼ ─ … « » “ ” ’`

Замены, которые используются в коде: `x` вместо `×`, `->` вместо `→`,
`-` вместо `−/–/—`, эмодзи вместо `✓ ⚠ ✎`.

В **комментариях** любые символы безопасны — Babel их выбрасывает.
Секция 1 и секция 9 тестов ловят это.

### 2. Optional chaining и всё новое из синтаксиса

Babel-пресет здесь только `react`, ничего не транспилируется.
Нельзя: `?.`, `??`, `||=`, `&&=`, `??=`, `Array.prototype.at`,
`structuredClone`, `Object.hasOwn`, числовые разделители `1_000`.

Вместо `a?.b` писать `a && a.b`. Секция 2 тестов ловит это.

### 3. Пропущенные запятые в объектных литералах

Node.js прощает часть таких ошибок, Babel на iOS — нет
(`Unexpected token, expected ","`). Это ломалось четыре раза: между `legs` и
`fullbody_a` в `WARMUP` и в `PROGRAM`, после `blocks: [...]` перед `avoid:`.
Секция 16 проверяет запятые **на любой глубине вложенности**.

### 4. Структурная целостность больших литералов

Блок упражнений, вставленный после закрывающей `};` объекта, Node принимает,
а Babel — нет (так уехал `posture_extra` из `ALTERNATIVES`). Секция 11
проверяет, что все ключи лежат внутри своих объектов и что нет дублей ключей
(был случай двойного `chest_stretch_extra`, где первая копия пустая).

### 5. iOS-специфика вёрстки

- `position: sticky` ломается, если на `body` стоит `overflow-x: hidden`.
  Поэтому в `head.html` используется `max-width: 100vw`.
- Любой `input` с `font-size < 16px` вызывает автозум. Поэтому глобально
  `input, button, select { font-size: 16px }`.
- Минимальная цель нажатия — **44pt** (Apple HIG). Секция 17 это проверяет.
- `env(safe-area-inset-*)` работает только с `viewport-fit=cover` в `<meta viewport>`.
- `apple-touch-icon` обязан быть **PNG в base64**. SVG data URI на iOS не
  работает — из-за этого приложение не ставилось на домашний экран на
  iPhone XR. Манифест — URL-encoded data URI с массивом `icons` 76/120/152/180.
- Таймер держится на абсолютном времени (`endsAtRef` + `endsAt` в
  localStorage), а не на счётчике тиков: иначе iOS усыпляет вкладку и отдых
  «замерзает».

### 6. Компилировать только после разбора страницы

Код приложения - inline-скрипт `#app-src` на ~290 КБ в конце страницы. Библиотеки
из `vendor/` (и из кэша воркера) загружаются мгновенно и могут обогнать парсер:
тогда `textContent` оборван на середине, и Babel падает с `Unterminated string
constant` на абсолютно целой строке. В Edge это ломало примерно каждую вторую
загрузку (с CDN гонку скрывала сетевая задержка). Поэтому и чтение исходника,
и `Babel.transform` идут внутри `onDocumentParsed(...)` в `head.html`. Не убирать:
тест это проверяет и падает без защиты.

## Как устроен `src/workout_tracker.jsx`

~3570 строк, один файл, порядок сверху вниз:

| | что |
|---|---|
| `WARMUP` | разминки по ключу дня. Ключи **обязаны совпадать** с ключами `PROGRAM` |
| `ALTERNATIVES` | ~60 групп замен: `exId -> [варианты]`. Пул ~210 упражнений |
| `PROGRAM` | пресеты: `push`, `pull`, `legs`, `fullbody_a`, `fullbody_b`, `fullbody_c` |
| `ACHIEVEMENTS` | только «постоянство»: стрики и количество тренировок. Иконка + название, без описаний и прогресс-баров |
| `WEEK_SCHEDULE` | дни недели |
| константы | `STORAGE_KEY = "ppl_tracker_v4"`, `HISTORY_LIMIT = 200`, `SESSION_KEEP_DAYS = 400` |
| `pruneOldKeys` / `loadData` / `saveData` | персистентность |
| `App()` | весь UI и вся логика, ~2400 строк |

### Контракт данных

Упражнение в пуле: `{ id, name, sets, reps, rest, steps, danger, warn }` —
все поля обязательны для всех 210 упражнений.

Разминка каждого дня обязана давать `label, sub, duration, why, avoid,
blocks[{ title, time, items[{ name, sets, tip, steps }] }]`.

Секция 19 **выводит список обязательных полей из самого рендера** — сканирует
обращения `wu.*`, `block.*`, `item.*`, `ex.*` в JSX. То есть добавил поле в
UI — оно автоматически стало обязательным во всех вариантах данных. Это
единственный паттерн, который реально остановил серию падений вида
`wu.avoid.map is not a function`. Не ломай его: не хардкодь список полей
обратно в тест.

### localStorage

Ключ `ppl_tracker_v4`:

| поле | что |
|---|---|
| `sessions` | незавершённая текущая работа, ключ `YYYY-MM-DD_день` |
| `history` | завершённые тренировки с `detail` |
| `swaps` | замены упражнений, **scoped по сессии** |
| `skipped` | пропуски, **scoped по сессии** |
| `customWorkouts` | свои дни из конструктора |
| `customSets` | изменённое количество подходов |
| `addedEx` | упражнения, добавленные на ходу |
| `resuming` | какая запись истории сейчас редактируется |
| `schedule` | массив из 7 элементов: ключ дня или `null` |
| `dbMode` | `"single"` / `"pair"` — вес за одну гантель или за пару |
| `trash` | удалённые записи для восстановления |

Таймер отдыха — отдельный ключ `sila_timer`.

Даты в ключах чистятся `pruneOldKeys` через 400 дней, история режется до
`HISTORY_LIMIT`. При восстановлении из корзины срез `HISTORY_LIMIT + 1`, иначе
восстановленная запись сразу отваливается.

### Поведение, которое легко сломать

- **Тренировку нельзя завершить пустой.** Нужно не меньше 3 упражнений, и
  упражнение считается выполненным только когда отмечены **все** его подходы.
  Упражнения-замены тоже учитываются.
- **Завершённая вручную тренировка не бывает «не закончена».** Бейдж
  «НЕ ЗАКОНЧЕНО» только у автосохранений (`src: "auto"`) с процентом ниже 100;
  запись с `src: "manual"` всегда «ЗАВЕРШЕНА». Кнопка «ДОПОЛНИТЬ» остаётся у
  любой записи, где выполнены не все подходы.
- **Вес отмеченного подхода менять нельзя, пока не снята отметка.** Поле
  `readOnly` (тап по нему подсказывает снять отметку), а `updateSet` сам не
  принимает `weight` у подхода с `done: true`. Иначе получался отмеченный подход
  без веса: журнал считал его выполненным («11/25»), а прогрессия и объём - нет
  («10 подходов»). Новый вес пишется заново при повторной отметке; прежний нигде
  не хранится.
- **«Объём» - это сумма весов отмеченных подходов, без повторов** (повторы мы не
  храним, они диапазонами). В сводке «за всё время» он показывается в кг, пока
  меньше 1000, дальше в тоннах с одним знаком (`formatVolume`).
- **Подход нельзя закрыть без веса.**
- **Каждый закрытый подход перезапускает отдых.** Снятие отметки — останавливает.
  Корень старого бага «таймер замер»: в `useEffect` зависимости были только
  `[timer.running]`, поэтому `startTimer` при уже идущем таймере гасил интервал
  и не пересоздавал его. Зависимости обязаны включать `timer.endsAt`.
- **Возобновление записи обновляет ту же запись**, не создаёт вторую. Сессия
  восстанавливается из `entry.detail` (веса, отметки, добавленные упражнения),
  потому что `finishWorkout` удаляет `sessions[sessionKey]` после сохранения.
  Есть кнопка отмены редактирования — она не должна удалять запись.
- **Прогрессия сортируется по строке даты ISO**, не по `ts`: у записей журнала
  `ts` — время сохранения, у восстановленных из `sessions` — полночь даты.
  Смешивание баз переставляет точки и показывает минус вместо плюса.
- **Подсказка «прошлый вес» и мини-график читают журнал, а не только `sessions`.**
  `finishWorkout` удаляет сессию после сохранения, так что у завершённых
  тренировок веса живут только в `history[].detail`. Источник один:
  `getPastExSets` (журнал, затем сессии как запасной вариант; сегодняшняя и
  дополняемая запись пропускаются).
- **Автоподстановка веса.** Пустое поле веса показывает серую подсказку
  (`getSuggestedWeight`): вес того же подхода прошлой тренировки; если сегодня
  уже введён предыдущий подход и он отличается от прошлого раза - копируется он.
  Отметка пустого подхода берёт подсказку и записывает её как настоящий вес.
  Нет подсказки (упражнение без истории) - по-прежнему «Впиши вес перед отметкой».
- **Резервная копия (экран «Мой план»).** `buildBackup` / `parseBackup` /
  `mergeBackup` стоят вне `App` и тестируются исполнением. Сохранение идёт через
  `navigator.share` с файлом (в iOS-PWA blob-скачивание ненадёжно), запасной
  путь - ссылка `download`. Загрузка **только добавляет**: журнал по `ts`
  (локальная запись побеждает при равном `ts`), сессии и прочее по ключу;
  `schedule` и `dbMode` берутся из файла лишь на устройстве без истории. Корзина
  и `resuming` в импорт не попадают. `data.lastBackup` - дата последней копии.
  Напоминание (`backupDue`): баннер на главном экране, если в журнале >= 3 записей
  и копия старше 14 дней или её не было; «ПОЗЖЕ» откладывает на 3 дня
  (`data.backupSnooze`). Пока в тренировке есть хоть один закрытый подход, баннер скрыт.
- **Подсказка прогрессии** (`getProgressionHint`): если в прошлый раз упражнение
  выполнено целиком (все подходы с весом, только по журналу - у сырых сессий нет
  числа запланированных подходов), предлагается рабочий вес + шаг (штанга и
  тренажёры 2.5, гантели 2, при «общем» весе пары 4). Повторы не хранятся, так что
  это только подсказка. Видна, пока в упражнении ничего не введено; «ВЗЯТЬ»
  заполняет только пустые неотмеченные подходы.
- **Экран не гаснет** (Screen Wake Lock): пока открыта вкладка «Тренировка» или
  «Разминка», приложение видно и `data.keepAwake !== false` (переключатель в «Мой
  план»). Система снимает замок при сворачивании - эффект берёт его заново по
  `visibilitychange`. Нет поддержки или отказ - молча без замка. Требует iOS 16.4+;
  в установленном на домашний экран PWA на iOS ранее 18.4, по имеющимся сведениям,
  замок не держится - проверять на телефоне.
- **Даты считаются по местному времени.** `todayKey()` не использует
  `toISOString()` (это UTC и вчерашнее число после полуночи).
- **`dbMode` фиксируется в записи** на момент сохранения и не применяется к
  истории задним числом.
- В селекторе дня показываются **только дни, назначенные в расписании**.
- **Фильтр журнала** (`filterJournal`, вне `App`): чипы по дням, которые есть в
  журнале, и поиск по названию упражнения. Слова запроса ищутся по отдельности
  в любом порядке, регистр и ё/е не важны. Под найденной записью показывается
  максимальный вес этого упражнения. Записи без `detail` запрос не находит.
  Состояние фильтра (`journalDay`, `journalQ`) в localStorage не хранится.
- Вкладки: тренировка, журнал (история + прогрессия), достижения. Отдельной
  вкладки «история» нет — она слита в журнал.

GitHub Pages репозитория `shattersxd/workout` раздаёт `index.html` из ветки
`main`, корень репозитория (вместе с `vendor/` и `sw.js`). Публикация занимает
полминуты-минуту.

Service worker (`sw.js`, кэш `sila-v6`): `vendor/*` - сначала кэш, страница -
сначала сеть, но не дольше 3 с (в зале связь бывает плохая), затем копия из
кэша. После деплоя новая версия приходит при ближайшем открытии, когда сеть
отвечает, так что на телефоне достаточно закрыть и открыть приложение. Старые
кэши чистятся при активации. Воркер должен быть файлом по URL: blob-воркеры
браузеры не регистрируют (прежний воркер из blob, скорее всего, не работал и
офлайна не было). `fetch`-обработчик не трогает не-GET и чужие домены. Логика
проверяется исполнением настоящего `sw.js` на заглушках (секция 22, асинхронные
тесты идут через `testAsync`, а не `test`: `test` не ждёт промисы).

Публикация идёт только через GitHub Pages, других хостингов нет.
