# Соц-функции: варианты и что закладываем заранее

Статус: **проектирование**. Сервера пока нет, поэтому сегодня в приложении нет ничего, что
уходит с телефона. Этот документ - карта вариантов, чтобы выбрать путь осознанно, а не
переписывать данные позже.

Ограничения, из которых исходим:

- Приложение - статический PWA на GitHub Pages, данные лежат в `localStorage` телефона.
  Хостинг не умеет ни аккаунтов, ни базы, ни приватных данных.
- Пользователь пока один; друзья - гипотетические. Цена ошибки в приватности высокая:
  вес, возраст, травмы - это данные о здоровье.
- iOS-PWA: нет надёжной фоновой синхронизации, push работает только у установленного на
  «Домой» приложения при явном разрешении (iOS 16.4+). Значит, синхронизация идёт при открытии.

## 1. Что именно называем «соц-панелью»

| Уровень | Функции | Нужен сервер |
|---|---|---|
| 0 | Карточка недели или рекорда картинкой (через «Поделиться»); ссылка или код на свою программу; сравнение двух людей через обмен файлами | нет |
| 1 | Друзья по коду-приглашению, недельный рейтинг (регулярность, объём), лента событий (закончил тренировку, рекорд), реакции; **соревнования для тех, кто тренируется прямо сейчас** (комнаты, см. раздел 9) | да |
| 2 | Группы и клубы, челленджи с целью («12 тренировок за месяц»), общая библиотека программ, комментарии, напоминания друзей | да, плюс модерация |

Рекомендуемый порядок: 0 -> 1 -> 2. Каждый уровень полезен сам по себе и не требует
переделки предыдущего.

## 2. Варианты бэкенда

| Вариант | Плюсы | Минусы | Подходит, если |
|---|---|---|---|
| **Supabase** (Postgres, Auth, Realtime, правила доступа на уровне строк) | Готовые аккаунты, реальная база, правила приватности описываются в SQL, лента в реальном времени, есть бесплатный тариф для старта | Лимиты и пауза неактивных проектов на бесплатном тарифе надо проверить на момент запуска; нужно писать SQL и политики доступа | Нужны друзья, рейтинги, лента, и хочется быстро |
| **Firebase** (Auth + Firestore) | Очень зрелый офлайн-SDK, push, простой вход через Apple/Google | Привязка к Google, модель документов хуже для рейтингов и связей, свой язык правил | Ставка на офлайн и push |
| **Cloudflare Workers + D1/KV** | Дёшево, быстро, всё под вашим контролем, нет простоя | Аккаунты, лента, правила доступа пишутся вручную: больше кода и ответственности за безопасность | Хочется минимума внешних сервисов и есть желание писать API |
| **PocketBase / свой VPS** | Один бинарник, полный контроль, данные у вас | Вы отвечаете за HTTPS, бэкапы, обновления, доступность | Есть сервер и готовность его обслуживать |
| **Без центрального сервера** (WebRTC между телефонами, обмен файлами и ссылками) | Нет серверных расходов, нет чужих данных | Оба должны быть онлайн, NAT, нет ленты и рейтинга «всегда» | Только уровень 0 |
| **Зашифрованный блоб в хранилище** (R2/S3) | Синхронизация между своими устройствами и бэкап, сервер ничего не видит | Социальные функции невозможны (сервер не видит данные) | Нужен лишь перенос между устройствами |

Рекомендация: **Supabase**, пока друзья - десятки, а не тысячи. Если позже потребуются
push-уведомления и сильный офлайн, это не мешает дублировать часть на Firebase Cloud
Messaging. Решение стоит принять до уровня 1, не раньше.

## 3. Аккаунты и вход

| Способ | Что нужно | Плюсы | Минусы |
|---|---|---|---|
| **Анонимный аккаунт + код друга** | Ничего | Нет почты и паспорта, низкий барьер, приватность по умолчанию | Потеряли телефон - потеряли аккаунт, если нет резервного входа |
| **Ссылка на почту (magic link)** | Почта | Просто, есть восстановление | Письма, антиспам, письмо открывается в Safari, а не в PWA |
| **Sign in with Apple** | Аккаунт Apple Developer (платный) | Привычно на iPhone, скрытая почта | Платная программа, настройка домена |
| **Google** | Проект Google Cloud | Привычно | Лишний сторонний вход для спортивного приложения |
| **Passkey (WebAuthn)** | Поддержка на сервере | Безопасно, без паролей | Сложнее реализация и поддержка |

Рекомендация: **анонимный аккаунт + код друга** на старте, затем привязка почты или Apple
для восстановления. Вход через OAuth в PWA на iPhone уже показал риск (разные контексты
хранилища, см. Spotify в CLAUDE.md), поэтому любой вход нужно проверять на телефоне до
того, как строить на нём остальное.

## 4. Что публиковать: модель приватности

Принцип: **публикуем производные показатели, а не сырые данные, и только с согласия
по каждой категории**. По умолчанию всё закрыто.

Публикуется (если включено): имя для друзей, число тренировок за неделю, объём недели,
серия недель по плану, дата последней тренировки, рекорды (название упражнения, вес,
дата) за 14 дней.

**Никогда не публикуется**: профиль (возраст, рост, вес, травмы), вес тела, самочувствие,
журнал целиком, заметки, токены Spotify. Это проверяется тестом на заготовке
`socialSummary`.

Прочее: рейтинг по **регулярности и относительным показателям**, а не по абсолютному весу
на штанге (иначе честного сравнения нет и демотивирует новичков); блокировка и жалоба на
пользователя; удаление аккаунта и всех данных одним действием; модерация имён и
аватаров; возрастной порог (приложение рассчитано на взрослых, см. анкету).

## 5. Синхронизация: офлайн-первая

- Телефон остаётся источником правды. На сервер уходит **очередь событий** (`workout_finished`,
  `pr`, `settings_changed`), каждое с UUID: повторная отправка безопасна (идемпотентность).
- Журнал - append-only: конфликтов почти нет. Настройки - «последняя запись побеждает»
  по `updatedAt`. Удаления - «надгробия» (`deletedAt`), иначе удалённое воскреснет с другого
  устройства.
- Лента и рейтинг читаются при открытии вкладки и по таймеру, пока она открыта; push - позже.
- Все записи с версией схемы: сервер и клиент обновляются не одновременно.

## 6. Что закладываем СЕЙЧАС (дёшево и обратимо, только в тестовой версии)

Сделано в `src/beta/social.jsx`, ничего не отправляется:

1. `data.schemaVersion` - версия формата данных и место для миграций.
2. `data.identity.userId` - случайный UUID, создаётся на устройстве, не содержит личных
   данных; позже станет ключом связи с аккаунтом. Из него же выводится читаемый код друга.
3. `data.social` - согласия: включено ли, имя для друзей, что публиковать (по категориям).
4. `socialSummary(data, today)` - чистая функция: ровно тот пакет, который в будущем уйдёт на
   сервер. Уже сегодня видно, **что именно увидят друзья**, и это покрыто тестами.
5. `socialLeaderboard(summaries, metric)` - рейтинг по регулярности или объёму.
6. Интерфейс бэкенда (`signIn`, `publishSummary`, `getFriends`, `addFriendByCode`,
   `getLeaderboard`) и локальная заглушка: интерфейс можно собрать и проверить до появления
   сервера, а потом подменить реализацию.
7. Соревнования «сейчас» (`src/beta/compete.jsx`): четыре формата, живой пакет только со счётчиками
   (без весов), табло с честными ничьими, боты для холодного старта, комнаты в локальной заглушке
   (`createRoom`, `joinRoom`, `publishLive`, `getRoom`, `subscribeRoom`) и демо-комната в интерфейсе.

Не сделано намеренно (затрагивает боевые данные, нужен отдельный осторожный шаг):

- Идентификатор тренировки. Сейчас тренировка опознаётся по `ts`; при дополнении записи
  `ts` сохраняется, а при слиянии двух устройств он может совпасть. Перед синхронизацией
  нужен `id` (UUID) и `updatedAt` у каждой записи с миграцией старых.
- `schemaVersion` и `identity` в боевых данных и в файле резервной копии.

## 7. Вопросы, которые надо решить до уровня 1

1. Сколько человек в «команде» (3-5 друзей или открытое сообщество)? Определяет сервис и
   модерацию.
2. Нужны ли push-уведомления (друг закончил тренировку)? На iOS это работает только для
   установленного PWA.
3. Кто платит и кто обслуживает сервер? Это решает между Supabase/Firebase и своим VPS.
4. Достаточно ли анонимного входа с кодом друга, или нужна привязка почты/Apple?
5. Что считаем «честным» рейтингом: регулярность, объём или прирост к своему прошлому?
6. Какие данные допустимо хранить на сервере по вашим правилам и законодательству вашей
   страны (данные о здоровье чувствительны)?
7. Соревнования: только комнаты друзей по коду или ещё и открытые «на сегодня» с незнакомцами?
   Открытые требуют модерации имён и жалоб.
8. Допустимы ли боты в комнатах друзей? Рекомендация: в комнатах друзей по умолчанию выключены.

## 9. Соревнования для тех, кто тренируется прямо сейчас

Идея: комната на время тренировки (обычно час), где участники видят общий прогресс в реальном
времени. Это отдельная механика рядом с друзьями и недельным рейтингом: она про «здесь и сейчас».

### 9.1 Форматы

| Формат | Что считается | Что уходит в комнату | Честность | Токсичность |
|---|---|---|---|---|
| **Больше подходов** | число закрытых подходов за окно | счётчик подходов | не зависит от силы | средняя (гонка) |
| **Выполнение плана** | доля запланированных на сегодня подходов | процент | годится для разных программ | средняя |
| **Личные рекорды** | сколько упражнений выше СВОЕГО прошлого максимума | число | соревнуешься с собой | низкая |
| **Командная цель** | общая сумма подходов против цели | счётчик | неважна | минимальная: рейтинга нет |

Принцип: **в комнату уходят счётчики, а не веса**. Вес на штанге раскрывает силу и состояние,
и по нему честного сравнения нет.

### 9.2 Как собираются комнаты

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **Комната друзей по коду** | создаёте, друзья входят по коду | безопаснее всего, не нужна модерация | нужны друзья онлайн |
| **Открытая комната на сегодня** | автоподбор по уровню (новичок, средний, опытный) и ближайшему часу | всегда есть кого догнать | нужны модерация имён, жалобы, блокировки |
| **«Сейчас в зале»** | просто видно, сколько людей тренируется, без очков | мотивирует без давления | нужен присутствующий поток людей |
| **Призрак** | гонка с собственной лучшей тренировкой | работает без людей и без сервера | нужны отметки времени у каждого подхода (сейчас их нет) |

### 9.3 Передача данных в реальном времени

| Способ | Особенности |
|---|---|
| **Опрос раз в 10-15 секунд** | проще всего, работает на любом бэкенде; задержка допустима для подходов раз в 1-3 минуты |
| **Realtime-подписка (Supabase, Firestore)** | мгновенно, меньше трафика в простое, но привязка к сервису |
| **WebSocket (Cloudflare Durable Objects, свой сервер)** | полный контроль, больше кода |

Ограничение iOS: PWA живёт в фоне плохо, поэтому обновления идут, пока приложение открыто.
Экран во время тренировки не гаснет (Wake Lock), так что для комнаты это не проблема. Push-уведомления
внутри соревнования не нужны.

### 9.4 Справедливость и защита от накруток

- Время «когда достиг счёта» ставит **сервер**, а не телефон; повторная отправка того же счёта
  время не меняет. Так «кто раньше» нельзя подделать (реализовано в заглушке, есть тест).
- Ничья решается так: раньше достиг, затем по имени, чтобы порядок не прыгал.
- Лимит скорости: не больше N подходов за M секунд. Для этого нужны отметки времени у каждого
  подхода (сейчас хранится только отметка «сделано»). Это изменение боевых данных, отдельный шаг.
- Правдоподобие: счёт, резко выбивающийся из истории человека, помечается для проверки.
- Комнаты друзей работают на доверии и без проверок.

### 9.5 Боты для холодного старта

Проблема: человек не должен оказаться один в пустой комнате. Решение (идея заказчика): сначала
комната «наполняется» ботами, затем люди постепенно их вытесняют. Правила:

1. **Боты не выдаются за людей.** Их поведение максимально естественное, но они помечены ненавязчиво:
   маленький значок 🤖 у имени и строка в шапке комнаты («1 человек и 4 бота-партнёра»). Крупного
   слова «БОТ» нет, но и скрывать нельзя: в комнатах настоящие люди, которые думают, что соревнуются
   с людьми. Скрытые боты - это обман пользователей (и риск для доверия, и претензии магазинов
   приложений и регуляторов). Это решение зафиксировано тестом.
2. **Детерминированы**: бот - чистая функция от (зерно комнаты, прошедшие минуты). Все телефоны
   считают одних и тех же ботов без серверной логики и без поддельных записей в базе.
3. **Ведут себя как люди**: приходят к старту не одновременно, подходы закрываются неровно (разный
   отдых между ними, редкие длинные паузы), есть быстрые и медленные, часть участников бросает
   тренировку на середине. Темп откалиброван по вашему журналу (множитель 0.75-1.25), поэтому гонка
   близкая, а не заведомо проигранная или выигранная.
4. **Люди вытесняют ботов с конца списка**: остальные боты сохраняют имя и прогресс, поэтому табло
   не «прыгает». В полной комнате ботов нет.
5. **Боты не попадают** в недельные рейтинги, серии, рекорды и ленту: это только фон соревнования.
6. Включаются и выключаются настройкой; в комнатах друзей по умолчанию выключены.
7. Интерфейс показывает, сколько людей в комнате на самом деле.

Альтернатива и дополнение: **призрак** (гонка с собой), если участников нет совсем.

Риски: давление «не отстать» не должно толкать к перетренированности. Поэтому соревнование
рекомендуется пропустить, если самочувствие последних тренировок низкое (данные уже есть в
`feelLog`), а в командном формате рейтинга нет вообще.

### 9.6 Что уже в коде (`src/beta/compete.jsx`, сеть не используется)

- `SOCIAL_FORMATS` - четыре формата с описанием и тем, что публикуется.
- `socialLiveProgress`, `socialLivePayload` - живой прогресс текущей тренировки (подходы, процент
  плана, рекорды); пакет содержит только счётчики.
- `socialCompRank`, `socialTeamProgress` - табло и командная цель.
- `socialBot`, `socialBotLive`, `socialRoomBoard` - боты и вытеснение людьми.
- `socialLocalRooms` - комнаты в локальной заглушке: создание, вход по коду, публикация, подписка.
- Демо-комната в интерфейсе: ваши подходы настоящие, соперники и «подключённые люди» имитация.
